# tagma — Architecture & Portability (draft)

Companion to `SPEC.md`. The spec defines the language; this documents how
implementations are built, bound, and shipped.

## Strategy

The **spec + conformance vectors** are the portable artifact, not any single
codebase. Rust provides the reference implementation; other languages either
bind it or port it, validated by the same vectors.

- **Reference implementation**: Rust workspace — core library + CLI. Must pass
  100% of conformance vectors.
- **Conformance suite**: Gherkin feature files under `features/`, first-class
  deliverable covering tag string → parsed triple (or error), infix query →
  postfix, and postfix + fixture tagset → matching ids. The step vocabulary is
  frozen (see `docs/steps.md`); each language runs the *same* features through
  its native cucumber runner (cucumber-rs, cucumber-js, behave, godog) by
  implementing only those steps against its binding or port.
- **Bindings** where FFI is idiomatic: Python (PyO3/maturin), JS (WASM),
  Swift/Kotlin (uniffi), Elixir (rustler). C ABI `cdylib` for everything else
  (C#, Java via Panama FFM, Ruby, PHP, Lua).
- **Native ports** where ecosystem culture rejects native deps: Go (weekend-
  sized against the vectors; wazero-hosted WASM is the no-cgo middle option).

## API constraint (load-bearing)

The core's public surface is **data-in/data-out over an opaque handle**:
strings in (tags, queries), id arrays out, index state inside the core. No
callbacks, traits, or host-language objects cross the boundary. Every FFI
mechanism above degenerates to trivial under this shape; it cannot be
retrofitted cheaply.

## Infix is a gateway (load-bearing)

Every implementation has exactly one query evaluator: the postfix stack VM.
Infix is a compiler front end and nothing more (SPEC.md §5). Each surface's
infix entry point is a two-line composition, `compile` then the postfix
entry point, and each surface also exposes `compile` so callers can obtain
the postfix that will run:

| Surface | infix entry | compiles via | then runs |
|---|---|---|---|
| tagma-core | `Index::query` | `infix::compile` | `Index::query_postfix` → `postfix::eval` |
| tagma-cli | `query <q>` | (`Index::query`) | `query --postfix <q>` path |
| C ABI (`include/tagma.h`) | `tagma_query` | `tagma_compile` | `tagma_query_postfix` |
| Python | `Index.query` | `tagma.compile` | `Index.query_postfix` |
| WASM / JS | `Index.query` | `compile` | `Index.queryPostfix` |
| Go port | `(*Index).Query` | `Compile` | `(*Index).QueryPostfix` → `evalPostfix` |

The bindings all delegate to tagma-core's `Index::query`; the Go port mirrors
it independently. Each surface carries a test pinning
`query(q) == query_postfix(compile(q))` over a shared table of queries. Do not
add an infix evaluator, an infix-only optimisation, or an infix-only API: add
it over postfix and let infix reach it by compiling.

## JS/TS packaging

Ship **WASM-only** — one npm package, no per-platform native addon matrix, no
postinstall, runs in Node/Deno/Bun/browser/edge:

- Build with wasm-bindgen (wasm-pack or hand-rolled equivalent); wrap the
  generated glue in a small hand-written TS ergonomic layer; `.d.ts` shipped.
- ESM with conditional `exports` (`browser` / `node` / `default`); `.wasm`
  shipped as a separate file for streaming instantiation and caching, with an
  optional base64-inlined entry for bundler-hostile environments.
- napi-rs native addons are the escalation path if WASM overhead ever matters;
  not part of v1.

## Interchange & serialization — no protobuf in the core

The tag grammar **is** the serialization format: every tag position (bare or
quoted — SPEC.md §2's QUOTING extension) round-trips as a plain string.
Boundary types are strings and u64 id arrays; nothing needs a schema
compiler.

- **Bulk dump/ingest**: line-oriented text — `<item-id> <tag> <tag> ...` per
  line (or JSONL where structure is wanted), fields split on *unquoted*
  whitespace so a quoted tag value containing a literal space stays one
  field (SPEC.md §2). Greppable, diffable, spec-defined by the tag grammar
  itself.
- **Query wire form**: the postfix string, already canonical.
- **Conformance suite**: Gherkin (human-authored, diffable, executable).
- **Index persistence/snapshot**: internal implementation detail, explicitly
  out of spec (any Rust-side format; consumers never parse it).
- **Protobuf/gRPC**: never in the core, where a schema-compiler dependency
  in every language would undercut the spec-is-portable stance. One message
  sits beside it: `tagma.v1.Tag` (`proto/tagma/v1/tag.proto`), the parsed
  triple, for a consumer that stores or sends tags inside its own protobuf
  messages (ctxloom's event-sourced task store is the first). Its Rust types
  are `crates/tagma-proto`, generated by prost at build time (protoc on
  PATH; generated code is never committed), with conversions to and from
  `tagma_core::Tag`. It depends on prost and tagma-core only, and nothing in
  the workspace depends on it. The tag string is still the portable form:
  the message carries decoded components, and `Display for Tag` spells them.

## Rules: validate and check (SPEC.md §10–§15)

The schema facets (`permit`, `enum`, `range`, `keys-per-item`, plus the
existing `arity` and `type`) and the two calls that read them live in `tagma-core`'s `rules`
module. Nothing in the write or query path changes: writes stay infallible
and queries ignore these facets.

Public shape (Rust reference; ports mirror it in their own idiom):

- `Rules` — the derived rule set, the counterpart of `HideConfig`:
  `Rules::from_tags(tags)` reads `tagma.*` config tags out of any tag
  collection (for a client, like taskloom, whose store is not an `Index`);
  `Rules::register_type(name, cmp)` adds a §9 comparator;
  `Rules::validate(current, &Change) -> Vec<Finding>` and
  `Rules::check() -> Vec<Finding>` are pure.
- `Index::rules()` derives a `Rules` from the whole store plus its
  registered comparators; `Index::validate(id, &Change)` and
  `Index::check()` delegate to it, keeping the handle-based,
  data-in/data-out constraint above: tags and an id in, findings out.
- `Change { add: Vec<Tag>, remove: Vec<Tag> }`;
  `Finding { code: Code, tag: Tag, args: Vec<(String, String)>, origin: Origin }`;
  `Code` is a closed enum whose `as_str()` is the stable kebab-case code
  from SPEC.md §13/§14 — the string is what crosses an FFI boundary.
  `Origin` is `Introduced` or `Existing` (`as_str()`: `"introduced"`,
  `"existing"`): a validate finding is `Existing` iff the same
  `(code, tag, args)` finding holds for the item's current set under the
  same config (SPEC.md §13 "Introduced or existing"; a `too-many-keys`
  compared without its `keys` args, §15); every check finding
  is `Existing`. A client refusing writes refuses on `Introduced` only.

Every surface exposes both calls, against an index and against a
standalone rule set built from config tags the caller holds itself
(`Rules::from_tags` — a client, like taskloom, whose store is not an
`Index`) — the "every surface exposes the same capabilities" rule the
infix-gateway table above follows. Bindings delegate to tagma-core; the Go
port mirrors the `rules` module independently:

| Surface | against an index | standalone rules | finding |
|---|---|---|---|
| tagma-core | `Index::validate(id, &Change)`, `Index::check()` | `Rules::from_tags(tags)`, `register_type`, `validate(current, &Change)`, `check()` | `Finding { code: Code, tag: Tag, args, origin: Origin }` |
| tagma-cli | `validate <id> [--add <tags>]... [--remove <tags>]...`, `check` (store on stdin) | `rules validate [--current <tags>]... [--add …]... [--remove …]...`, `rules check` (config tags on stdin, no ids) | one JSON object per stdout line |
| C ABI (`include/tagma.h`) | `tagma_validate(h, id, add, remove)`, `tagma_check(h)` | `tagma_rules_from_tags(tags)` → `TagmaRules`, `tagma_rules_validate(r, current, add, remove)`, `tagma_rules_check(r)`, `tagma_rules_free(r)` | one JSON object per line of the returned string (`tagma_str_free`) |
| Python | `Index.validate(id, add=[], remove=[])`, `Index.check()` | `Rules.from_tags(tags)`, `Rules.validate(current, add=[], remove=[])`, `Rules.check()` | `dict`, `args` a list of `(name, value)` tuples |
| WASM / JS | `Index.validate(id, add, remove)`, `Index.check()` | `Rules.fromTags(tags)`, `Rules.validate(current, add, remove)`, `Rules.check()` | `Finding` object, `args` as `[name, value]` pairs |
| Go port | `(*Index).Validate(id, Change)`, `(*Index).Check()` | `RulesFromTags(tags)`, `RegisterType`, `(*Rules).Validate(current, Change)`, `(*Rules).Check()` | `Finding{Code, Tag, Args []Arg, Origin}` |

Outside Rust and Go a finding's tag is its canonical spelling (SPEC.md
§2), and tags cross as strings: a whitespace-separated list split as an
ingest line is (CLI, C ABI), or one tag per list element (Python, JS). The
JSON object is `{"code":…,"tag":…,"args":[[name,value],…],"origin":…}` in
both the CLI and the C ABI. A `TagmaRules` handle has exactly
`TagmaIndex`'s guarantees, in its own registry under its own magic, so
neither kind of handle is ever accepted as the other. Registering a §9
comparator on a standalone rule set is possible only where comparators
are (tagma-core, Go): the other surfaces take no callbacks, for indexes
and rules alike.

Conformance: `features/rules.feature` pins validate/check across every
harness with four steps (`docs/steps.md`): cucumber-rs
(`crates/tagma-core/tests/conformance.rs`), cucumber-js
(`bindings/js/features-steps`), godog (`ports/go/conformance_test.go`) and
behave (`bindings/python/features/steps`, the feature symlinked in). No
step names the standalone form, so each harness's `When the config is
checked` also asserts that `Rules::from_tags` over every tag the scenario's
`Given` steps wrote checks identically to the index. Validate is not
cross-checked that way — an item's set is what the write path's §8
collapse left, which the written tags need not be — and is pinned per
binding instead.
